# ADR-004: התחברות, שמירת ה-session ויומן ההסכמות

**תאריך:** 2026-10-24
**סטטוס:** התקבל (ספרינט 1, F-003a). דודי סקר את הסכמה, ורז סוקר את הקוד.

## הקשר

בספרינט 1 נכנסת התחברות עם Google ומסך הסכמות חוסם (אפיון 4.1, 4.2). צריך להחליט:
- איפה שומרים את ה-session במכשיר.
- איך היומן מחזיק מעמד כראיה.
- איך מעלים שינויי סכמה לסביבות.

כל זה לפני שיש עשרות אלפי משתמשים, ובלי לבנות תשתית שלא נדרשת עכשיו.

## ההחלטה

**1. התחברות:** Google Sign-In נייטיב (`@react-native-google-signin/google-signin`) מחזיר ID token שהקהל שלו הוא לקוח ה-Web, ו-`supabase.auth.signInWithIdToken` ממיר אותו ל-session. ה-secret של לקוח ה-Web נמצא רק בדשבורד של Supabase.

**2. ה-session מוצפן במכשיר:** session של Supabase גדול מדי ל-SecureStore. לכן:
- הוא נשמר ב-AsyncStorage, מוצפן ב-AES-256-CTR (`aes-js`).
- לכל ערך יש מפתח אקראי משלו (`expo-crypto`), ורק המפתח נשמר ב-SecureStore (Android Keystore).
- מי שקורא רק את AsyncStorage לא רואה כלום.
- הקוד ב-`apps/mobile/src/lib/secureSessionStorage.ts`.

**3. יומן ההסכמות הוא ראיה:**
- **הוספה בלבד:** אין למשתמשים UPDATE, DELETE או TRUNCATE, וגם ל-service role אין TRUNCATE.
- **השרת קובע:** trigger קובע את `user_id` ואת `created_at` בשרת, ודוחה גרסה של תנאים או מדיניות שאינה הנוכחית (שגיאה 22023). האפליקציה מפרשת את השגיאה הזו כ"פורסמה גרסה חדשה" ומציגה את המסך מחדש.
- **מסמכים מפורסמים נעולים:** אחרי שגרסה פורסמה אי אפשר למחוק אותה, לשנות את המספר או התאריך שלה, או להחליף את הכתובת שלה. מפתח זר מהיומן לגרסה מבטיח שכל הסכמה מצביעה על מסמך קיים.
- **אין מפתח זר ל-`auth.users`:** היומן נשמר אחרי מחיקת חשבון (אפיון 8). תקופת השמירה נקבעת עם היועץ המשפטי, ומחיקה לפיה נבנית בספרינט 2.
- **עותק במכשיר:** המכשיר שומר עותק של הגרסאות שאושרו, כדי לדעת גם בלי רשת אם מסך ההסכמות חייב לחסום (AC-18a).

**4. הרשאות בכל טבלה חדשה:** Supabase נותן ל-`anon` ול-`authenticated` את כל ההרשאות על כל טבלה חדשה ב-`public`. RLS חוסם את הגישה בפועל, אבל ההרשאות עצמן נשארות. לכן כל migration שיוצרת טבלה, view או sequence מסתיימת ב:
- `revoke all ... from anon, authenticated`.
- `grant` רק של מה שצריך.
- `revoke execute` על פונקציות trigger.
- בדיקות pgTAP של `table_privs_are` שנועלות את זה.

**5. העלאת migrations:** בספרינט 1 ההעלאה ל-staging ידנית ומתועדת (`supabase db push` אחרי מיזוג ל-main). אוטומציה מ-CI ל-staging, כמו שהאפיון (8) מתאר, נכנסת כשיהיו כמה migrations בחודש. ה-CI כבר מריץ על כל PR את כל ה-migrations על מסד נקי, בדיקות pgTAP ו-`db lint`.

**6. גרסה 0 של המסמכים:** נכנסת ב-migration לכל הסביבות, כי מסך ההסכמות לא עובד בלעדיה. **פרסום גרסה 1, אחרי עו"ד, חוסם את ההעלאה ל-production.** יש בדיקה ברשימה שלפני ההשקה.

## חלופות שנשקלו

- **ה-session ב-SecureStore בלבד:** הגבול של כ-2KB לערך לא מספיק ל-session עם פרטי המשתמש.
- **ה-session ב-AsyncStorage בלי הצפנה:** כך גם Supabase מציעה כברירת מחדל. אבל ה-refresh token מאפשר להתחבר, ובמכשיר פרוץ או בגיבוי הוא חשוף.
- **`ON DELETE SET NULL` במקום בלי מפתח זר:** אז הרשומה מאבדת את הקשר לאדם, ואין לה ערך כראיה. אם מוחקים את הקשר, עדיף למחוק את השורה.
- **בדיקת הגרסה רק באפליקציה:** לקוח ישן או מניפולציה היו רושמים הסכמה לגרסה שלא הוצגה.

## השלכות

- **כל טבלה חדשה** צריכה את בלוק ההרשאות ואת הבדיקות שלו. זה נבדק בסקירה של דודי.
- **החלפת מכשיר:** אצל משתמש חוזר, ההסכמות נקראות מהשרת. אם אין רשת בפתיחה הראשונה במכשיר חדש, מסך ההסכמות מוצג (AC-18a).
- **מחיקת חשבון בספרינט 2** צריכה לרשום מאיזה מועד נספרת תקופת השמירה, כי אין מפתח זר שיגיד מתי החשבון נמחק.
- **לבחון מחדש:** כשיהיה אדמין לניהול מסמכים (אפיון 7), וכשהיועץ המשפטי יקבע אם לשמור גם hash של הטקסט שאושר (`content_sha256`).
