# סקירת אבטחה פנימית (ספרינט 13, AC-14 ו-AC-15)

**תאריך:** 2026-10-31
**מה נבדק:** הריפו ב-main אחרי v0.13.0, וה-APK של v0.13.0, אותו קוד.
**מה לא נבדק:** בדיקת חדירות חיצונית. היא בתשלום ונעשית לפני ההשקה (ספרינט 14).

## Edge Functions: מי רשאי לקרוא ומה נבדק בקלט

| Function | `verify_jwt` | מי רשאי לקרוא | בדיקת הקלט |
|---|---|---|---|
| `flight-lookup` | true | משתמש מחובר. המשתמש נקרא מהטוקן (`auth.getUser`) | `POST` בלבד. מספר טיסה ותאריך מאומתים (`bad_number`, ‏`bad_date`). יש מכסה למשתמש (`take_flight_lookup`) |
| `delete-account` | false (*) | משתמש מחובר: ‏`auth.getUser` על הטוקן, ואימות מחדש עם ID token של Google מאותו חשבון, עד 60 דקות | `POST` בלבד. בלי ID token מוחזר 400. חשבון אחר מחזיר 403 |
| `flight-watch` | false | `pg_cron` בלבד: ‏`CRON_SECRET` בכותרת (`hasCronSecret`) | `POST` בלבד. בלי סוד מוחזר 401 |
| `flight-coverage` | false | `pg_cron` בלבד: ‏`CRON_SECRET` | `POST` בלבד. ‏`action` וחלון מאומתים (`bad_action`, ‏`bad_window`) |
| `rates-daily` | false | `pg_cron` בלבד: ‏`CRON_SECRET` (נוסף בספרינט 13, דודי 2) | `POST` בלבד. בלי סוד מוחזר 401. ריצה נתפסת קודם במסד (`claim_job_run`, פעם בשעה לכל היותר) |
| `advisories-daily` | false | `pg_cron` בלבד: ‏`CRON_SECRET` (נוסף בספרינט 13) | כמו `rates-daily`. טקסט מוגבל ל-4000 תווים |

(*) ב-`delete-account` הפרויקט חותם טוקנים במפתח שהשער של Supabase לא מאמת, ולכן הפונקציה בודקת את הסשן בעצמה (ADR-006, סעיף 6).

**בסביבת הפיתוח:** ‏`load-seed-data` היא שארית חד-פעמית מטעינת הנתונים (30.10). היא מחזירה 410 לכל קריאה, ואין לה קוד בריפו. **מומלץ שיוסי ימחק אותה** מהדשבורד.

## סודות

### הריפו
- **gitleaks** רץ ב-CI על כל PR, על הקומיטים החדשים.
- **workflow חדש** (`security-scan.yml`) מריץ gitleaks על כל הקומיטים בכל הענפים:
  - פעם בשבוע.
  - לפי דרישה.
  - ב-PR שמשנה אותו.
  - **הריצה הראשונה:** ב-PR 23. התוצאה רשומה ב"הרצה" בהמשך.
- **מה לא נכנס ל-Git:** ‏`.env.local` ו-`google-services.json`. שניהם ב-`.gitignore`.

### ה-APK (נסרק ב-31.10, ‏v0.13.0)

מפתחות ציבוריים שמותר להם להיות ב-APK (רשימת היתרים):

| מה | למה מותר |
|---|---|
| מפתח Supabase מסוג `sb_publishable_…` | מיועד ללקוח. ההגנה היא RLS (ראו `rls-audit.md`) |
| טוקן Mapbox מסוג `pk.…` | טוקן ציבורי, עם הטלמטריה כבויה |
| ‏API key של Firebase (`AIza…`) | מזהה את הפרויקט ולא נותן הרשאה. **מומלץ להגביל אותו לחבילה ול-SHA-1** ב-Google Cloud Console (פעולה חינמית של יוסי) |

נבדק ולא נמצא:

| מה | תוצאה |
|---|---|
| `sk.` של Mapbox | 0 |
| `service_role`, או JWT עם `"role":"service_role"` | 0 |
| מפתח `sb_secret_` של Supabase | 0 |
| מפתח פרטי (`BEGIN … PRIVATE KEY`) | 0 |
| `CRON_SECRET` או מפתח של AeroDataBox / RapidAPI | 0 |

- **הערה על `sb_secret_`:** המחרוזת `sb_secret_` מופיעה ב-APK פעם אחת. זו הקידומת שהקוד בודק כדי לסרב למפתח סודי (`src/lib/supabase.ts`).
  - **למה הסורק תפס אותה:** ב-Hermes המחרוזות צמודות זו לזו בלי מפריד, ולכן סורק נאיבי קורא אחריה 47 תווים.
  - **הבדיקה:** מבנה התווים הוא אותיות קטנות ו-`_` בלבד, כלומר שמות עמודות ב-snake_case. מפתח אמיתי משלב אותיות גדולות, קטנות וספרות.
  - **מקור המפתח בבנייה:** ‏`.env.local` מכיל רק מפתח `sb_publishable_` באורך 46.

שלוש החולשות החמורות:

| חבילה | נכנסת דרך | למה לא חוסם |
|---|---|---|
| `node-forge` ≤1.4.0 (אימות חתימת RSA) | `@expo/cli` → ‏`@expo/code-signing-certificates` | כלי ה-CLI של Expo רץ במחשב הפיתוח ולא נארז ב-APK. אין לנו code signing של עדכונים (אין expo-updates) |
| `zod` <4.6.6 (צריכת זיכרון בקלט ענק) | `@expo/cli` (‏zod 3.25) | כלי בנייה. האפליקציה לא מייבאת zod |
| `@expo/cli` | התלויות שלמעלה | כלי בנייה |

- **בדיקה:** ה-JS שבתוך ה-APK נבנה רק ממה שהאפליקציה מייבאת. `@expo/cli`, ‏`node-forge` ו-`zod` לא נמצאים בו.
- **התיקון:** מגיע עם עדכון של Expo SDK, ולא בעקיפה ידנית של תלויות פנימיות. עקיפה כזו עלולה לשבור את הבנייה.
- **מתי בודקים שוב:** בכל עדכון SDK, ולפני ההשקה.
